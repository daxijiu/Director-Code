Phase 2 Provider / ACP / Plan 总体路线报告

日期：2026-05-15 ｜ 工作区：E:\Projects\Director-Code-batch\Director-Code-112-check ｜ 关联子报告：ACP、Provider UI、Plan Mode

总判断

  • 下一阶段不应被命名为单纯“ACP 接入”。更准确的范围是：Provider/Model Registry、External Agent Adapter、Plan Policy 三条线并行收束。
  • Claude Code 不走 ACP 优先，走 Claude Agent SDK TypeScript adapter。ACP 用于通用外部 Agent，包括 OpenCode、Hermes、Gemini、Codex ACP wrapper 等。
  • Provider UI 应在广泛外部 Agent 发布前完成。否则用户会在模型 provider、agent provider、mode/model picker 之间遇到同一套旧的单全局状态问题。
  • Plan Mode 应作为 mode/session policy 做，而不是只新增一个 agent config。Native Director、Claude SDK、ACP 都映射到同一套“只读计划、审批后执行”的产品语义。

四个核心决策

决策 建议 理由
Claude 接入方式 使用 @anthropic-ai/claude-agent-sdk TypeScript SDK。 VS Code 主线 Claude 集成也是 SDK 路径；SDK 原生支持 permission mode、Plan、canUseTool、MCP/plugins、session resume。
ACP 定位 作为通用 external agent adapter，而不是所有 agent 的强制中间层。 ACP 适合 session/mode/model/permission/event 标准化，但会削弱 Claude 专有能力。
Provider UI 先做 workbench 内部 registry + 两个 UI，再逐步插件化。 当前已有单全局状态 bug；完全插件化要等 proposed API、OAuth、internal service bridge 边界明确。
Plan Mode 做成可测试 policy profile，审批后切 Edit/Agent。 参考实现都说明 Plan 需要权限兜底和退出状态机，不只是 prompt 或 config 文件。

推荐顺序

  1. Vocabulary freeze：先在代码和 UI 文案中区分 LLM Provider、Model、External Agent、Agent Session、Plan Policy。避免把 provider 页面做成 agent 页面。
  2. Provider/Model UI wave：实现多 provider registry、Provider Manager、Model Catalog、chat picker provider grouping，并迁移旧配置。
  3. Claude SDK spike：以专用 adapter 接 Claude，完成 stream、cancel、permission、Plan、文件编辑 review 的最小闭环。
  4. ACP adapter wave：从 Hermes 或 OpenCode 开始，再试 Codex ACP wrapper。只要求 VS Code parity，不要求全部 Director tool registry 互通。
  5. Plan policy wave：把 native Director Plan、Claude Plan、ACP Plan 都映射到同一套 UI 和权限状态机。
  6. Codex decision gate：对比 ACP wrapper 与实际 VS Code/Codex extension 行为，决定是否需要专用 Codex adapter。

关于“Provider UI 是否必须在 ACP 前完成”：不必阻塞 Claude SDK / ACP 的技术验证，但应在正式用户可见的外部 Agent 聚合入口前完成。更现实的排法是 Provider UI wave 与 Claude SDK spike 并行，Provider UI 先进入 release candidate。

建议 Patch / Replay 归属

当前 AGENTS.md 要求长期源码真相是 replay control plane。后续代码落地时建议：

  • Provider registry/settings/model picker 改动优先归入现有 settings/chat built-in mode 相关 stage；若改动过大，可新增明确的 010-director-provider-registry.116.patch，并同步 patches/series.116.json、profile、patch generation classification。
  • External Agent adapter 可归入 004-director-agent-engine.116.patch，若文件量和依赖显著增加，则新增 010-director-external-agents.116.patch 更清晰。
  • Plan mode policy 与 mode routing 相关，可优先扩展 Phase 5 所在的 mode routing ownership。若影响 UI/session provider 较大，再单独拆 stage。
  • 任何 generated tree 调试成果必须回写 replay patch，完成前至少跑 profile-scoped replay validation。

Wave 最低验证 补充验证

建议立刻开的工程任务

  1. 写一份短 design doc：Provider Registry schema、External Agent Adapter interface、Plan Policy object 三个类型边界。
  2. 修 provider UI 的已知 bug：模型刷新结果不进入 UI、OAuth 只显示 active provider、API key status 被全局 provider 污染。
  3. 做 Claude TS SDK 版本 pin 和 adapter spike，先不提交大 UI，只验证 stream/permission/plan。
  4. 做 ACP adapter spike，优先 Hermes 或 OpenCode，因为本地仓库已有 ACP/plan 线索。
  5. 把 Plan Mode 的只读 policy 测试先写出来，避免后面 UI 推着安全边界走。

最终建议

下一波如果要命名，建议叫 Phase 2 External Agent and Provider Foundation，而不是只叫 ACP。它的 acceptance 应该是：

  • 用户能在 Provider Manager 中同时启用多个模型 provider，并在 Model Catalog 中控制 chat picker 显示。
  • Claude Code 通过 SDK 出现在 native Chat session 中，Plan/permission/edit review 可用。
  • 至少一个 ACP agent 通过通用 adapter 出现在 native Chat session 中，达到 VS Code parity。
  • Director native Plan 可以只读地产生计划，并在用户审批后进入 Edit/Agent。
