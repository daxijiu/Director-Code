Phase 2 Provider / Model UI 调研报告

日期：2026-05-15 ｜ 工作区：E:\Projects\Director-Code-batch\Director-Code-112-check ｜ 主题：多 Provider、模型可见性、Chat 模型分组

结论摘要

  • 当前 Director provider UI 是单全局 provider/model/baseURL/authVariant 设计，无法满足“多个 provider 同时激活、模型单独显示/隐藏、chat picker 按 provider 分组”的目标。
  • Provider UI 工作建议排在大规模 ACP 外部 Agent UI 之前。它不阻塞 Claude SDK 技术 spike，但应先于面向用户的多 Agent 发布。
  • Provider 与 Model 应分成两个界面：Provider Manager 管连接和认证，Model Catalog 管模型发现、启用/隐藏、显示名、能力和默认选择。
  • 可以参考 VS Code 公开 LanguageModelChatProvider API 和 oai-compatible-copilot 插件，但 Director 不宜立即完全迁移为普通扩展。推荐先做 workbench 内部 Provider Registry，再把可公开的 provider adapter 逐步插件化。

当前实现现状

当前 116 generated tree 的相关代码位于 vscode.generated/layers/director/vscode/src/vs/workbench/contrib/directorCode。

文件 / 服务 当前能力 问题
agentEngine.contribution.ts 注册 IApiKeyService、IOAuthService、IAuthStateService、IModelResolverService，注册单一 DirectorCodeModelProvider。 语言模型 provider vendor 固定为 director-code，chat picker 难以按真实 provider 分组。
providerSettingsWidget.ts 提供 provider、authVariant、model、baseURL 选择。 所有设置写入单全局 config：directorCode.ai.provider、directorCode.ai.model、directorCode.ai.baseURL、directorCode.ai.authVariant。这天然只能表达一个当前 provider。
apiKeysWidget.ts SecretStorage 中已有 provider-level 和 model-level key/config 结构。 UI 只像“多 provider key 列表”，但状态、测试和当前配置仍被全局 provider/baseURL/model 影响。
oauthWidget.ts 支持 Anthropic PKCE manual flow 和 OpenAI device code。 只展示当前 active provider 的 OAuth 行，不是 provider 管理页。
modelResolver.ts 已有按 provider/baseURL/auth identity/auth variant 组成的 cache key，并能 API/CDN/static 三层解析模型。 模型解析能力比 UI 先进。需要把 resolver 结果写入 Model Catalog，而不是只填单个 select。
DirectorCodeModelProvider 向 VS Code 语言模型服务暴露当前 provider 的模型。 metadata 只有单 vendor，且 custom/compatible 模型容易被全局 provider 推断污染。

目标信息架构

建议明确区分两个概念：LLM Provider 是“模型供应商或兼容 endpoint”，External Agent Provider 是“Claude Code / ACP Agent / Codex session”。本报告只处理 LLM Provider / Model UI。

Provider Manager

  • 每个 provider 是一个实例，而不是单纯 enum。一个用户可以同时有 openai-main、openrouter、local-ollama、company-proxy。
  • 字段建议：id、kind、displayName、enabled、baseURL、authType、authIdentityKey、createdAt、updatedAt、lastTest。
  • 操作建议：启用/停用、测试连接、刷新模型、OAuth 登录/注销/重置、API key 设置/清除、复制 diagnostics。

Model Catalog

  • 每个 provider instance 下维护模型列表，来源包括 API discovery、内置 catalog、用户手动添加。
  • 字段建议：providerId、modelId、displayName、enabled、hidden、family、contextWindow、capabilities、pricing、defaultForModes、lastSeen。
  • UI 建议：按 provider 分组的表格，搜索/过滤，批量显示/隐藏，刷新单 provider，显示 authentication/source 状态。

Chat 模型选择器

  • 只显示 enabled provider 下 enabled 且未 hidden 的模型。
  • 排序先按 provider，再按 pinned/default、能力、名称。
  • 优先用真实 provider 分组。实现上可探索两条路：每个 provider instance 注册独立 language model provider vendor，或在单 provider metadata 中填充稳定 category。需要用 116 内部 model picker 实测。

插件化可行性

VS Code 官方 Language Model Chat Provider 文档说明，扩展可以通过 vscode.lm.registerLanguageModelChatProvider 注册自己的语言模型 provider，并提供模型 metadata、token count 和 chat request 实现。oai-compatible-copilot 已经证明 OpenAI-compatible provider 可以用这条公开 API 做出来。

方案 优点 限制 建议
完全内置 workbench 实现 能直接使用现有 Director service、SecretStorage、Chat Editing、内部 model picker 细节。 代码继续落在 replay patch，边界不够清爽。 适合作为第一阶段，先把数据模型和 UI 修正。
完全内置扩展实现 结构清晰，接近 VS Code 生态，provider adapter 可独立演进。 需要确认 proposed API、secret storage、OAuth、本地 Director agent/tool policy 是否都能通过 extension API 表达。 不建议一步到位。
混合方案 Provider Registry 和权限桥留在 workbench，协议 adapter / public LM provider 可以逐步放入 built-in extension。 需要设计稳定 internal command/service bridge。 推荐。先内核，后插件化。

建议：先实现 Director Provider Registry 和两个原生管理界面，再在第二步把 OpenAI-compatible provider adapter 抽到 built-in extension。这样可以修当前 bug，同时不把未来插件化路线堵死。

与 ACP 工作的先后关系

Provider UI 不阻塞 Claude SDK adapter 或 ACP adapter 的技术验证，因为外部 Agent session 不等于 LLM model provider。但是它应该优先于“正式发布多外部 Agent 体验”。原因是：

  • 用户会把 Provider、Model、Agent 三个入口混在一起理解。Provider UI 如果仍是单全局状态，多 Agent 接入后会更混乱。
  • Claude SDK adapter 可以独立使用 Claude OAuth/Copilot/Anthropic auth，但 Codex、OpenAI-compatible 模型和 Director native agent 需要清晰 provider/model registry。
  • Chat model picker 的 provider 分组要求会影响 model provider registration 方式，越晚改影响越大。

建议工作包

  1. 新增 provider instance registry 和 settings migration。保留旧 config 读取，将其迁移为一个默认 provider instance。
  2. 重做 Provider Manager UI：多 provider 列表、enabled toggle、URL/API key/OAuth login/logout/reset/test。
  3. 新增 Model Catalog UI：按 provider 分组的模型发现、启用/隐藏、手动添加、刷新和 diagnostics。
  4. 重写 DirectorCodeModelProvider 的模型发布逻辑，使 chat picker 只见用户启用模型，并按 provider 分组。
  5. 修复现有 refresh models 不回填 UI、OAuthWidget 只显示 active provider、API key 状态受全局 provider 污染等 bug。
  6. 补充迁移和 picker 行为测试，再做 clean materialize + replay validators。
